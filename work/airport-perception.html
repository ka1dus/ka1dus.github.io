Real-time surveillance perception

A patrolling security robot streams one wide camera feed. The job was to watch it for fire, falls, running, crowding, fights and unattended bags all at once, on one GPU, and to turn each detection into an alert the robot fleet can act on.

01

Six models, one GPU, no lag

Each use case needs a different model and different logic, but they all share the same frames and the same GPU. The runtime makes sure a slow model never stalls the video or the other detectors.

  • One shared grabber keeps only the newest frame. RTSP is forced over TCP with low-latency FFmpeg flags, so lossy Wi-Fi doesn’t produce torn frames and detectors always analyse now.
  • One thread per detector, each at its own pace. A heavy model (crowd density at 1280 px) just updates its label less often.
  • Every frame normalised to the robot camera’s 2048×576 panorama, with rectangular inference at 1280×384 so no compute is wasted on letterbox padding.
  • A shared output contract (status + label) for every detector, so adding a new model is one small class and it shows up in the UI automatically.
02

Faster with TensorRT, and provably the same

Because all detectors share one GPU, what matters is the total GPU time per sweep. I exported the YOLO models to TensorRT FP16 engines and wrote a benchmark harness that measures both raw model latency and the deployed per-frame cost through the real detector code.

One full sweep of all six detectors dropped from 53.1 ms to 38.0 ms, about 28% less GPU time. That headroom is what lets one card run the models more often, or take on more detectors.

Checking accuracy without labels

A faster engine is only useful if it still finds the same things. With PyTorch FP32 as the reference, both ran over the same 286 frames per model, and every box was matched at IoU 0.5.

03

From detection to an alert someone acts on

Each detection becomes an alert in the robot fleet’s platform, tied to the robot and camera that saw it, with a clean snapshot attached.

  • Resolves camera → robot from the stream, creates the alert, then uploads the snapshot as its preview image.
  • Sent from a background queue, so a slow network never blocks detection.
  • OAuth tokens renew automatically, network errors and 5xx responses retry with backoff, and each alert type fires at most once every 20 s to avoid floods.
  • Each detector debounces its trigger. An alert latches only after it persists for several frames, with a cooldown before it can fire again, so one noisy frame doesn’t page anyone.

Alongside this I built Grafana dashboards over the fleet’s fault-reporting logs, so errors on deployed robots could be pinned down without digging through raw logs.

04

PPE detection on a quadruped, in the field

I took real-time PPE detection from concept to a live client demo on a quadruped robot in an aircraft hangar in under three days. The robot walks the hangar floor and flags anyone missing required safety gear.

The constraints were the opposite of the airport pipeline’s.

  • Edge device, not a desktop GPU. Detection runs on the robot itself, so the model and frame size had to fit its compute budget while staying real-time.
  • A moving camera. A walking robot sees people at changing distances and angles, which is harder than the fixed cameras most PPE models are trained on.
  • A live audience. The client watched it run in their own hangar, so it had to work first time, in their lighting, with their people.
