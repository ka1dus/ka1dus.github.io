Patrol-robot operator assistant

Operators at a command console run a fleet of rideable patrol robots. When something goes wrong they call a service hotline. This assistant lets them fix common issues themselves, and it is built so that when it doesn’t know, it says so rather than sounding confident and wrong.

01

Answers from the manual, or a handoff

The assistant answers only from the console’s user guide. Every answer cites the guide entries it used, and anything the guide doesn’t cover goes straight to the hotline.

It also writes for its reader. Operators send tasks from the console, and officers ride the robots. So the console’s own actions are direct instructions (“Send the Undock task”), the officer’s are third person, and it never tells operators to “inform the console”, which would mean contacting themselves.

02

Don’t trust the model’s confidence

Open-weight 7–32B models are much worse than frontier models at knowing what they don’t know. So the decision to escalate doesn’t rest on the model’s self-report. The safety guarantees live in code, not in the prompt.

Three checks, independent of the model

  • Citation verification. The model must name the entry IDs it used. An ID that doesn’t exist, or wasn’t in the retrieved context, forces escalation, because a fabricated citation is the fingerprint of a fabricated answer.
  • Grounding gate. The retrieval score is a model-free signal of whether the guide covers the question at all. I measured in-scope and out-of-scope score ranges and set the threshold as a backstop.
  • Confidence floor, fail closed. Low confidence escalates, and so does every error path.

Why both kinds of retrieval

The manual is full of exact terms like “Go Park”, “Undock” and “ENABLE”. Dense embeddings handle paraphrase but miss rare exact tokens, and BM25 is the reverse. Operators ask both kinds of question, so both run and the rankings are fused with reciprocal rank fusion.

Schema order matters

Constrained decoders generate fields in schema order. With answer first, a small model would write a good answer and then mislabel it. Putting sources first makes it commit to its evidence before classifying, and that fixed a real misclassification bug.

03

A bigger model didn’t fix it. Code did.

Schedule questions (“who is charging at 9am?”) came back wrong about a third of the time, confidently. Retrieval was correct and the citation was real. The model simply misread a row of a six-row table.

Schedule questions (8)llama3.1:8bqwen2.5:14b
Model reads the table5/85/8
Lookup computed in a resolver8/88/8

Identical scores from both models, failing on different questions, showed it was a task problem, not a capacity problem. So a resolver parses the time, finds the slot in structured data and adds a “computed for this question” line before the model sees the entry. Resolvers only add context, never replace it, so one that doesn’t fire falls back to the old behaviour.

Rule of thumbAnything the model must calculate rather than read belongs in code.
04

Latency you can plan for

I profiled where the time goes and sized the deployment from it. Decode speed is a hard floor set by memory bandwidth (9.3 tok/s for the 14B model on a 16 GB laptop, about 86 tok/s on a 24 GB GPU server with vLLM).

  • Keeping the model resident removed a ~10 s reload after idle periods.
  • Retrieving 4 entries instead of 8 cut ~425 prompt tokens per question with no loss of recall, since every correct entry already ranked #1 or #2.
  • A bounded request queue returns “busy, retry shortly” under load instead of letting latency grow, and every reply logs its elapsed time.
  • Admin-key auth for the web UI, a CLI for self-tests and threshold tuning, and a pytest suite covering the guardrails.
